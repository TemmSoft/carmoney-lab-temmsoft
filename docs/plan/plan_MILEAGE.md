# plan_MILEAGE — правило «пробег не больше 400 000 км, иначе review»

Задача: в расчёт решения по заявке добавить проверку пробега: пробег не больше
400 000 км — решение по LTV без изменений; пробег больше 400 000 км — решение
`review`.

Сверка с `docs/setup/code_map.md` **не состоялась: файла нет**. В `docs/setup/`
лежат только `mcp.md`, `tools.md`, `permissions_check.md`. План построен по
прямому чтению кода; если у заказчика есть актуальная карта кода — см. вопрос 4.

Семантика по умолчанию (выбрана консервативная, см. вопрос 1): итоговое решение
— худшее из LTV-решения и правила пробега. Пробег может понизить `approve` до
`review`, но **не смягчает** `reject` и не меняет уже вычисленный `review`.

## Тесты

Граничные значения — отдельной строкой:

- 399999 — пробег 399 999, LTV в зелёной зоне → `approve`.
- 400000 — пробег ровно 400 000 («не больше» — граница включительно), LTV в
  зелёной зоне → `approve`.
- 400001 — пробег 400 001, LTV в зелёной зоне → `review`.
- пустой пробег — в payload нет ключа `mileage` → `ValidationException` с
  ошибкой по ключу `mileage`; решение не вычисляется (валидатор отсекает
  раньше движка).

Дополнительные случаи (не граничные):

- Пробег 400 001 + LTV в reject-зоне → `reject` (правило не смягчает отказ).
- Пробег 400 001 + LTV в review-зоне → `review` (остаётся review).
- Пробег 0 → валиден, решение по LTV.
- Пробег 500 000 → валиден (жёсткий лимит 500 000), решение `review`.
- Пробег 500 001 → 422 от валидатора, regression-фиксация существующего
  поведения `max_mileage_km`.
- В `DecisionEngineTest` существующие кейсы переносятся с нейтральным пробегом
  (например, 84 000) — решение по ним не меняется.

Конвенции: AAA, тест заканчивается assert'ом, имя описывает поведение.

## Риски

- **Взаимодействие с `max_mileage_km` (500 000).** Диапазон 400 001–500 000
  становится «валидно, но review» — это и есть задача. Лимит валидации, её
  сообщение «Пробег от 0 до 500000 км» и сам валидатор не меняются.
- **Смена контракта конструктора `DecisionEngine`.** Все три места сборки
  (AppFactory:37, AssessmentServiceTest:27, DecisionEngineTest `setUp()`) должны
  обновиться одним коммитом; пропущенное место — падение на этапе сборки
  приложения/тестов.
- **Коэрцезия пустой строки в PHP:** `(int) '' === 0`, а фронтенд отправляет
  `Number('') === 0` — пустое поле формы уходит как 0 км и проходит валидацию.
  Тест «пустой пробег» закрывает только отсутствие ключа в JSON; поведение
  «пустое поле UI = 0 км» планом не меняется (вопрос 2).
- **Смена формы провайдера `ltvValues()`.** Все 7 существующих кейсов
  переезжают на новую форму; при небрежной миграции сломается отчёт
  DataProvider, а не логика.
- **БД.** `decisions.decision` — ENUM('approve','review','reject'): `review`
  уже есть, миграция схемы не нужна; заявки с пробегом 400 001–500 000 начнут
  сохраняться со статусом `review`. Сид (пробег 20 000) не затронут.
- **Не входит:** задача LOAN-12 (лимит по `ltv_by_age`), правки валидатора и
  его сообщений, фронтенд, README, сид/схема БД, feature-тесты HTTP-уровня
  (вопрос 5), коммит/PR — по отдельному указанию заказчика.
